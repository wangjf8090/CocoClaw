# Skill 编写指南：Failure Modes & Troubleshooting 章节规范

> **目标**：把"实战踩坑经验"沉淀为可复用、可检索的 Skill 章节，让其他 Agent 调用时能直接参考。
> **来源**：从 `agent-memory-system-guide` 和 `ai-text-detox` 两个 Skill 的实战经验提炼。

---

## 一、为什么需要这个章节？

SKILL.md 描述「Skill 能做什么」，但**不描述「Skill 什么时候会失败 / 失败后怎么救」**。

实战中，Agent 经常遇到：
- Skill 调用后产物不符合预期
- 不知道哪里出问题，只能重试
- 重试还是失败，又不知道下一步

**Failure Modes & Troubleshooting 章节** = 把"踩过的坑 + 修复 SOP"沉淀进 Skill，让 Agent 自助排障。

---

## 二、章节结构模板

每个 Skill 的 `## ⚠️ Failure Modes & Troubleshooting` 章节，建议按以下结构组织：

```markdown
## ⚠️ Failure Modes & Troubleshooting

本章节记录 [Skill 名称] 的**典型失败场景**、**失败原因**和**具体修复方法**，
而非泛泛的"检查步骤"。

### 场景 1：[场景一句话描述]

**失败原因**：[为什么会出现这个失败，深层原因]

**判断标准**：
- [可观测的判断条件 1]
- [可观测的判断条件 2]
- [可观测的判断条件 3]

**修复流程**：
\`\`\`bash
# 具体的修复命令或步骤
[step 1]
[step 2]
\`\`\`

**安全替代方案**（如有风险操作）：
\`\`\`bash
# 更安全的做法
[safe approach]
\`\`\`

### 场景 2：[场景一句话描述]
...（重复上述结构）

### 风险操作 [N]：[操作描述]

**风险等级**：🟢 低 / 🟡 中 / 🟠 中高 / 🔴 高

**为什么危险**：
- [风险点 1]
- [风险点 2]

**禁止行为**：
\`\`\`bash
# 不要这样做
[bad pattern]
\`\`\`

**安全替代方案**：
\`\`\`bash
# 推荐做法
[safe pattern]
\`\`\`
```

## 三、典型场景模板（按 Skill 类别复用）

### 模板 A：内容处理类 Skill（如 ai-text-detox）

| 场景 | 失败原因 | 修复方向 |
|------|---------|---------|
| 处理后丢失原文核心观点 | 过度追求"指标达标"删除实质内容 | 识别核心主张 + 检查具体数据/证据保留 |
| 处理后产生新 AI 痕迹 | 只机械删除连接词，没重建自然流 | 合并并列结构 + 改变序号方式 |
| 技术文档丢失精确性 | 当作普通文章处理 | 保留 API 名/技术指标/代码示例 |
| 法律合规风险 | 简化关键条款 | 法律专业人士审核 + 区分关键 vs 描述 |

### 模板 B：记忆/状态类 Skill（如 agent-memory-system-guide）

| 场景 | 失败原因 | 修复方向 |
|------|---------|---------|
| SESSION-STATE 过期 | 重启后读到旧状态，新对话已切换任务 | 备份旧状态 + 重新生成候选新状态 |
| 记忆污染（被错误信息写入） | 写入前未做事实核查 | 加 source 字段 + 写入前自检 |
| crontab 误触发 | 自动写入覆盖人工决策 | crontab 只做只读 + 写入需人工确认 |
| memory/ 误入 git | daily notes 含敏感信息 | .gitignore 排除 + 独立加密备份 |
| 临时决策未沉淀 | 任务结束直接关闭 | 任务结束 30 秒内写 working-buffer.md |

### 模板 C：通用模板

| 场景类型 | 触发条件 | 修复模式 |
|---------|---------|---------|
| 输出格式异常 | 长度/编码/结构不对 | 加后处理脚本兜底 |
| 上游数据缺失 | 第三方 API 失败 | 降级到备用数据源 |
| 状态不一致 | 多次操作冲突 | 加锁 + 事务回滚 |
| 性能瓶颈 | 大数据/复杂计算 | 分批 + 缓存 + 异步 |

## 四、判断标准写法（关键）

判断标准要**可观测、可量化**：

| ❌ 模糊 | ✅ 具体 |
|--------|--------|
| 改写效果不好 | 改写后字数减少 > 30% |
| 状态过期了 | `## 当前任务` 字段在当前会话从未提及 |
| 数据有问题 | daily notes 包含 source 字段缺失的条目 |
| 操作有风险 | crontab 触发写操作 / git add memory/ |

**原则**：Agent 看到判断标准后，能不依赖人直接判断"我这个 case 是不是命中"。

---

## 五、修复流程写法（关键）

修复流程要**可执行、可验证**：

| ❌ 描述性 | ✅ 可执行 |
|---------|---------|
| 检查一下配置 | `cat ~/.config/app.yaml \| grep -E "key1\|key2"` |
| 重新生成状态 | `python3 scripts/state_gen.py --workspace /path` |
| 备份数据 | `cp -r memory/ memory-backup-$(date +%Y%m%d).bak` |
| 回滚版本 | `git checkout HEAD~1 -- SKILL.md` |

**原则**：Agent 复制粘贴命令就能跑，跑完能验证是否解决。

---

## 六、风险操作写法（关键）

涉及**不可逆**或**对外**操作时，必须标风险等级 + 禁止行为 + 安全替代：

```markdown
### 风险操作 N：[操作名]

**风险等级**：🟠 中高风险

**为什么危险**：
- [具体风险点 1：数据丢失 / 不可逆 / 对外可见]
- [具体风险点 2]

**禁止行为**：
\`\`\`bash
# 不要这样做（注释说明为什么错）
[bad command]
\`\`\`

**安全替代方案**：
\`\`\`bash
# 推荐做法
[safe command]
\`\`\`
```

**风险等级图例**：

| 等级 | 含义 | 必须包含 |
|------|------|---------|
| 🟢 低风险 | 可逆/对内 | 修复流程 |
| 🟡 中风险 | 部分不可逆 | 修复流程 + 安全替代 |
| 🟠 中高风险 | 不可逆 / 涉及敏感数据 | 禁止行为 + 安全替代 + 备份建议 |
| 🔴 高风险 | 对外 / 不可恢复 | 禁止行为 + 强制人工确认 |

## 七、章节长度建议

| Skill 复杂度 | 场景数 | 章节行数 |
|------------|--------|---------|
| 简单 Skill（单功能） | 2-3 | 100-200 行 |
| 中等 Skill（多功能） | 4-6 | 200-400 行 |
| 复杂 Skill（多功能 + 集成） | 6-10 | 400-700 行 |

**原则**：覆盖 ≥80% 实战失败场景，但不追求穷举（剩下 20% 用"其他问题 → 反馈到 Skill 作者"兜底）。

---

## 八、章节维护流程

| 时机 | 动作 |
|------|------|
| **新失败场景出现** | 在章节末尾追加新场景（"场景 N+1"） |
| **修复方案变更** | 修改对应场景的"修复流程"，版本号 bump |
| **场景失效**（不再出现） | 保留但加 deprecated 标记，不要直接删 |
| **新风险操作** | 加新"风险操作 N"节 |
| **每月一次** | 复盘：哪些场景最常触发 → 优化 Skill 本身减少失败 |

## 十、Checklist（新 Skill 发布前自检）

- [ ] 至少覆盖 3 个典型失败场景
- [ ] 每个场景有「失败原因 + 判断标准 + 修复流程」三件套
- [ ] 不可逆操作有「风险等级 + 禁止行为 + 安全替代」三件套
- [ ] 所有判断标准可观测、可量化
- [ ] 所有修复流程可执行、可验证（命令可复制粘贴）
- [ ] 章节行数在合理范围（见第七节）
